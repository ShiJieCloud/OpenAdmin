# 用 View Transition API 实现主题切换的圆形扩散动画

> 仿 [Element Plus 官网](https://element-plus.org/)，从 API 原理、设计推演到工程落地的完整方案

## 写在前面

[Element Plus 官网](https://element-plus.org/) 有一个让人眼前一亮的主题切换效果：点击切换按钮后，会有一个从点击位置向外圆形扩散的动画，平滑完成亮色与暗色模式的过渡。这个动画能明确告诉用户"主题从哪里开始变化"——这在交互上是一种比瞬间切换更友好的反馈，体验感拉满。

本文记录我在 Vue 3 项目中复刻这个效果的完整过程：从认识 View Transition API，到推演空间与时间两条策略，再到最终落地到 Pinia Store。过程中踩过的"闪白""方向反了"坑，也会一并讲清根因。

技术栈：Vue 3 + TypeScript + Pinia + View Transition API + CSS `@keyframes` 与 `clip-path`。

## 一、View Transition API：浏览器给的前件

要实现"新旧主题快照之间的过渡"，最朴素的想法是截图 + 动画。而 View Transition API 把这件事变成了浏览器原生能力，核心流程只有四步：

```
调用 startViewTransition(callback)
       ↓
浏览器对当前页面截图 → 生成 ::view-transition-old(root) 伪元素
       ↓
执行 callback（在此更新 DOM）
       ↓
浏览器对新页面截图 → 生成 ::view-transition-new(root) 伪元素
       ↓
浏览器自动播放 cross-fade 过渡动画
       ↓
过渡完成，移除伪元素，显示真实 DOM
```

两个关键伪元素分别是切换前、切换后的页面快照：

| 伪元素 | 说明 |
|--------|------|
| `::view-transition-old(root)` | 切换前页面快照 |
| `::view-transition-new(root)` | 切换后页面快照 |

默认情况下，`old` 在底层、`new` 在顶层，浏览器自动播放 cross-fade。但这只是默认行为——我们可以通过 CSS 完全覆盖它，自定义任意动画。本文要做的圆形扩散，就是建立在这层覆盖之上。

## 二、第一道坑：方向反了

拿到 API 后，最容易想到的写法是：让顶层的 `new` 快照从点击点扩散开来，覆盖底层的 `old`。

这对"亮→暗"是成立的：`new`（暗色快照）从点击点扩散，视觉上暗色从点击处铺开，方向正确。

但"暗→亮"时会出问题。如果同样让 `new`（亮色快照）扩散，表面看也合理；可一旦深入推演首末帧，就会发现：暗→亮时真正"主动"的应该是亮色，而亮色此刻在 `new` 上，让 `new` 扩散方向是对的——但如果改用 `old` 在顶层做收缩动画，首帧就会先露出底层 `new`（亮色），整屏先变亮一次再扩散，方向反而错了。

这个推演说明：**单向策略无法同时覆盖两个方向**，必须按方向分流。

## 三、空间策略：让亮色始终主动扩散

基于上面的推演，我把策略收敛成一句话：**让"亮色"始终做主动动画，暗色在底层被动变化。**

| 切换方向 | 谁在顶层 | 动画类型 | clip-path 变化 | 视觉效果 |
|---------|---------|---------|---------------|---------|
| 亮→暗 | old（亮色快照） | 收缩擦除 | `circle(endRadius)` → `circle(0)` | 亮色从满屏缩到点击点，暗色从四周露出 |
| 暗→亮 | new（亮色快照） | 扩散揭示 | `circle(0)` → `circle(endRadius)` | 亮色从点击点扩散到满屏，覆盖暗色 |

为什么暗→亮必须用 `new` 而不是 `old`？把三帧展开看：

- 让 `old`（暗色）在顶层扩散：首帧 `clip-path: circle(0)` → 暗色几乎不可见 → **页面先变亮**（露出底层 `new`）；动画中暗色从点扩散到满屏 → **方向反了**；末帧暗色满屏 → 伪元素销毁 → **闪屏回到亮色**。
- 让 `new`（亮色）在顶层扩散：首帧 `circle(0)` → 亮色仅点击点可见 → **页面保持暗色**；动画中亮色从点扩散到满屏 → **方向正确**；末帧亮色满屏 → 伪元素销毁 → **无缝过渡**。

空间策略到这里已经保证"动画过程方向正确"。但只解决空间问题还不够——还有一个时间维度上的陷阱在等着。

## 四、时间策略：守住伪元素的首帧

空间策略讲的是"动画过程方向正确"，但 View Transition 还有一个"首帧"陷阱：**浏览器一旦创建 `::view-transition-old/new(root)` 伪元素，会立即首次绘制，不会等我们的动画代码。**

这对"暗→亮用 `new` 扩散"是直接威胁：

- 暗→亮时，`new` 伪元素首绘那一刻，`clip-path` 理应是 `circle(0)`（亮色仅点击点可见）。
- 若此时 CSS 规则尚未注入，`new` 伪元素会以**默认满屏状态**绘制一帧 → 整屏先变亮一次 → 再开始扩散 → **闪白**。

也就是说，空间策略的成败，最终落在"伪元素诞生那一刻，规则是否已经就位"。于是空间策略必须配上时间策略：

| 维度 | 要求 | 手段 |
|------|------|------|
| 空间 | 亮色主动扩散，方向正确 | clip-path 起止值 + 顶层选择 |
| 时间 | 伪元素首绘时规则已就绪、首帧已锁定 | 动态 `<style>` 先注入 + `animation-fill-mode: both` |

落到具体操作上有两条约束：

1. **注入时机**：动态 `<style>` 必须在 `startViewTransition` 调用之前注入，保证伪元素创建时 `clip-path` 规则已就绪。
2. **首帧锁定**：用 `@keyframes` + `animation-fill-mode: both`（其 `backwards` 模式），让伪元素一出现就以 `from` 帧的 `clip-path` 绘制，而非默认满屏。

这两条约束决定了后续完整时序：先算坐标、先注入样式，再调 `startViewTransition`，最后在 `transition.finished` 里清理。

## 五、完整实现

### 5.1 时序流程

把空间与时间两条约束拼起来，完整的调用时序如下：

```
① 计算点击坐标 (x, y) 和 endRadius
       ↓
② 动态创建 <style> 元素，写入 @keyframes + 伪元素规则
   └─ 必须在 startViewTransition 之前完成：
      伪元素创建时 CSS 规则已就绪，首帧立即应用 clip-path
       ↓
③ 调用 startViewTransition(callback)
   ├── 浏览器捕获 old 快照（当前主题页面）
   ├── 执行 callback → setThemeMode + nextTick（DOM 更新为新主题）
   └── 浏览器捕获 new 快照（新主题页面）
       ↓
④ 伪元素创建 → @keyframes 动画立即开始
   └─ animation-fill-mode: both 的 backwards 模式
      确保首帧 clip-path 在伪元素绘制时就生效
       ↓
⑤ 动画播放（500ms ease-in-out）
       ↓
⑥ transition.finished → 移除 <style> 元素，清理追踪变量
       ↓
⑦ 伪元素销毁，显示真实 DOM（无缝过渡）
```

关键约束是步骤②必须在③之前。如果 `<style>` 在伪元素创建后才注入，伪元素首帧会以默认状态（无 `clip-path`）绘制，出现满屏闪白。

### 5.2 Pinia Store 中的 toggleTheme

```typescript
import { ref, watch, computed, nextTick } from 'vue'
import { defineStore } from 'pinia'
import { THEME_MODE } from '@/types/modules/theme'

export const useThemeStore = defineStore('theme', () => {
  const isDarkMode = ref(false)
  const themeMode = ref(THEME_MODE.Light)

  const setThemeMode = (mode: ThemeMode) => {
    themeMode.value = mode
  }

  // 追踪动态注入的 <style> 元素
  let vtStyleEl: HTMLStyleElement | null = null

  const toggleTheme = (event: MouseEvent) => {
    const doc = document as Document & {
      startViewTransition?: (cb: () => Promise<void>) => {
        finished: Promise<void>
      }
    }
    const isSwitchingToDark = !isDarkMode.value
    const targetMode = isSwitchingToDark ? THEME_MODE.Dark : THEME_MODE.Light

    // 不支持 View Transition API 时直接切换
    if (typeof doc.startViewTransition !== 'function') {
      setThemeMode(targetMode)
      return
    }

    // 点击坐标 & 视口最远角距离
    const { clientX: x, clientY: y } = event
    const endRadius = Math.hypot(
      Math.max(x, innerWidth - x),
      Math.max(y, innerHeight - y),
    )
    const circle = (r: number) => `circle(${r}px at ${x}px ${y}px)`

    // 双向层级策略
    const active = isSwitchingToDark ? 'old' : 'new'
    const from = isSwitchingToDark ? circle(endRadius) : circle(0)
    const to = isSwitchingToDark ? circle(0) : circle(endRadius)

    // 清理上一次残留的 <style>
    vtStyleEl?.remove()

    // 动态注入 CSS @keyframes + 伪元素样式
    const el = document.createElement('style')
    el.textContent = `
      @keyframes vt-clip {
        from { clip-path: ${from}; }
        to   { clip-path: ${to}; }
      }
      ::view-transition-old(root),
      ::view-transition-new(root) {
        animation: none;
        mix-blend-mode: normal;
      }
      ::view-transition-${active}(root) {
        z-index: 9999;
        animation: vt-clip 500ms ease-in-out both;
      }
    `
    document.head.appendChild(el)
    vtStyleEl = el

    const transition = doc.startViewTransition(() => {
      setThemeMode(targetMode)
      return nextTick()
    })

    // 过渡结束后清理
    transition.finished
      .catch(() => {})
      .then(() => {
        el.remove()
        if (vtStyleEl === el) vtStyleEl = null
      })
  }

  return { isDarkMode, themeMode, setThemeMode, toggleTheme }
})
```

其中 `endRadius` 取的是点击点到视口四个角的最远距离：

```js
const endRadius = Math.hypot(
  Math.max(x, innerWidth - x),
  Math.max(y, innerHeight - y),
)
```

这样能保证圆形扩散到 `endRadius` 时正好完全覆盖整个视口，不会留下边角漏色。

### 5.3 组件调用

逻辑全在 Store 里，组件侧只需绑定事件：

```vue

  placement="bottom"

    <el-icon>

```

```vue

```

## 六、为什么是 @keyframes 而不是 Web Animations API

这里单独拎出来讲，是因为它是整个方案中"时间策略"的内核，也对应了前面提到的首帧陷阱。

最初我用的是 `element.animate()`（Web Animations API），在 `transition.ready` 回调里启动动画：

```js
transition.ready.then(() => {
  root.animate({ clipPath: [...] }, { duration: 500, ... })
})
```

但伪元素在 `transition.ready` resolve **之前**就已经创建并首次绘制了。此时 `root.animate()` 尚未执行，伪元素以默认状态（无 `clip-path`，满屏可见）显示了一帧 → **`new` 满屏闪白**。

根因很清楚：**Web Animations API 是"事后接管"动画，但伪元素的首帧已经画完了。** 要让首帧也受控，得换到声明式的 CSS 动画上：

```css
@keyframes vt-clip { from { clip-path: circle(0); } to { clip-path: circle(500px); } }
::view-transition-new(root) {
  animation: vt-clip 500ms ease-in-out both;
}
```

关键在 `animation-fill-mode: both`——它包含 `backwards` 模式，会在动画正式开始前就应用 `from` 帧的样式。于是伪元素创建时**首帧就是 `circle(0)`**，不会出现满屏闪白。这与"动态 `<style>` 先注入"是同一件事的两面：先注入保证规则就位，`both` 保证首帧锁定。

## 七、工程化细节

把核心逻辑跑通后，还有几处工程化细节决定了它能不能上生产。

### 7.1 快速连点的 DOM 积累

用户快速连点主题按钮，`<head>` 会积累多个 `<style>` 标签。处理上分两步：

```js
// 创建新 <style> 前移除上一个
vtStyleEl?.remove()
```

同时用闭包变量追踪，确保 `finished` 回调只移除自己对应的元素：

```js
transition.finished
  .then(() => {
    el.remove()                    // 闭包捕获，移除自己对应的元素
    if (vtStyleEl === el) vtStyleEl = null  // 防止误清新引用
  })
```

这里 `if (vtStyleEl === el)` 的判断不能省：用户连点时，新一次切换会先把 `vtStyleEl` 指向新的 `<style>`，旧动画的 `finished` 回调随后才触发；若不加判断直接置空，会把新引用误清掉，导致下一次清理失效。

### 7.2 组件卸载时的内存泄漏

如果动画进行中组件被卸载，`transition.finished` 的回调可能不执行，`<style>` 永久残留。常规做法是 `onBeforeUnmount` 清理，但本方案把 `toggleTheme` 提取到了 Pinia store（单例，应用级生命周期）——Store 的生命周期与整个应用一致，`transition.finished` 总能正常 resolve，从根上规避了组件级泄漏问题。

### 7.3 不支持 View Transition API 的浏览器

Safari 等浏览器可能不支持。做特性检测并降级到直接切换即可：

```js
if (typeof doc.startViewTransition !== 'function') {
  setThemeMode(targetMode)
  return
}
```

降级路径不影响主题切换功能本身，只是丢了动画——对功能可用性零影响。

## 八、完整时序回顾

把前面所有约束串起来，整个流程的完整时序如下，作为收尾：

```
用户点击主题按钮
       ↓
特性检测：startViewTransition 是否可用？
       ↓ 可用
计算点击坐标 (x, y) 和 endRadius
       ↓
vtStyleEl?.remove()  ← 清理上一次残留
       ↓
创建 <style> 元素，写入 @keyframes + 伪元素规则
       ↓
document.head.appendChild(el)
       ↓
调用 startViewTransition(callback)
       ├── 浏览器捕获 old 快照（当前主题页面）
       ├── 执行 callback → setThemeMode + nextTick（DOM 更新为新主题）
       └── 浏览器捕获 new 快照（新主题页面）
       ↓
伪元素创建 → @keyframes 动画立即开始（fill: both 首帧生效）
       ↓
动画播放（500ms ease-in-out）
       ↓
transition.finished → el.remove() + vtStyleEl 清理
       ↓
伪元素销毁，显示真实 DOM（无缝过渡）
```

回头看，这个效果看起来只是一个圆形扩散动画，背后却串起了浏览器渲染时序、CSS 动画首帧锁定、空间与时间两条策略的协同，以及工程化层面的 DOM 清理与降级。理解了这些约束的因果，再去做类似的"伪元素 + 动画"场景时，就不必再走一遍试错路径了。
